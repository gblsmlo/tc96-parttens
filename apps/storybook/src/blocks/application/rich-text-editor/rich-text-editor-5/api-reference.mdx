# RichTextEditor5

A writing assistant that edits through suggestions. The document is a rollout plan that takes the whole page, the assistant is a chat card inset in the bottom corner over it, and every edit the assistant makes lands in the text as a suggestion you accept or reject. Reach for it when an assistant should propose and a person should decide, such as a plan, a policy or a help article. Install it with `npx @tc96/cli add rich-text-editor-5`.

The tasks are fix spelling, tighten wording, write a summary, add a checklist, list open questions and list owners. The card is built from the COSS chat and composer: an empty state lists the six tasks, `/` in the composer (or its lightning button) opens the same list, and a typed request picks the task by keyword; a request it cannot match is answered with three suggested tasks. Each request is an outgoing message and each answer an incoming message from "Assistente" with the status, the steps and the findings, with a typing indicator while a run is active. The card collapses to a button in the same corner, with the count of pending suggestions, and the bubble above a selection opens it again. Fix spelling, tighten wording and write a summary can be limited to a selected passage: the bubble runs "Resumir" or "Corrigir ortografia" directly, or hands the passage to the composer. A run can be stopped and writes its edits behind a labelled caret ("Assistente"). The review sits in the latest answer: it steps through each edit as a was/now pair with accept, reject, accept all and reject all, and the last decision undoes in one step. The two review tasks answer with findings that jump to their text and edit nothing.

There is no formatting toolbar: the page is plain text with the assistant as the only tool. The page header comes from the consumer through `navbar`, composed with `Navbar1` in the stories.

The block is controlled: it never fetches or persists, and the app receives the document and the decisions through callbacks. The assistant has no model behind it; see The planner seam.

## RichTextEditor5

| Prop | Type | Default | Description |
| --- | --- | --- | --- |
| `author` | `{ id: string; name: string }` | required | The current user. Your own typing is a direct edit stamped with this id; the assistant always writes as a separate author. |
| `defaultValue` | `RichTextValue` | required | The document, read once. |
| `planner` | `RichTextEditor5Planner` | the local planner | Decides what a task does: steps to show, edits to write and findings to list. See The planner seam. |
| `stepDelay` | `number` | `450` | Milliseconds between steps and edits. `0` runs a task at once, which is what tests use. |
| `formatTime` | `(date: Date) => string` | `Intl` pt-BR, short date and time | Formats the time of each suggestion in the review list. |
| `onChange` | `(value: RichTextValue) => void` | - | Called with the document, suggestions included, on every edit and every decision. |
| `onDecision` | `(decision: RichTextEditor5Decision) => void` | - | Called after Accept, Reject, Accept all or Reject all. Undo is not a decision. |
| `navbar` | `ReactNode \| ((context: RichTextEditor5NavbarContext) => ReactNode)` | - | The page header, rendered above the plan. As a function it receives `status` (a badge with the running task or the pending count, `null` when there is neither), `pending` (the number of suggestions) and `running`. |
| `labels` | `Partial<RichTextEditor5Labels>` | pt-BR texts | Overrides the texts of the block; see Labels below. |
| `className` | `string` | - | Merged into the root classes. |

## The planner seam

`planAction(task, source, scoped?)` is the local planner: no model, only fixtures (known typos, two canned rewrites, a fixed summary, a fixed checklist, and scans for questions, TBDs and tasks naming a teammate). It is the seam to swap for your own model. Pass a `planner` and the block calls it with a request; the block writes whatever it returns.

```ts
type RichTextEditor5Planner = (request: {
  task: RichTextEditor5Task
  text: string
  selection: string | null
  signal: AbortSignal
}) =>
  | RichTextEditor5Plan
  | Promise<RichTextEditor5Plan>
  | AsyncIterable<RichTextEditor5PlanEvent>
```

`text` is the whole document, one line per block joined by a newline; `selection` is the selected passage in the same shape, or `null`. `signal` aborts when the user presses Stop. Return a plan (`{ steps, edits, findings }`) or stream events from an async generator, one `step`, `edit` or `finding` at a time; the block waits `stepDelay` after each one.

| Edit | Shape | Result |
| --- | --- | --- |
| `replace` | `{ type: 'replace'; find: string; text: string }` | The first occurrence of `find` (inside the passage when one is set) becomes a deletion plus an insertion. |
| `insert` | `{ type: 'insert'; after: string; text: string }` | `text` is inserted right after `after`. |
| `add-block` | `{ type: 'add-block'; block: 'p' \| 'action_item'; text: string; after?: string }` | A new block, whose text is an insertion, goes after the block that contains `after`, or at the end. |

A finding is `{ id, kind: 'question' \| 'tbd' \| 'owner', text, quote }`; `quote` is the exact text the Go to button selects and scrolls to. An edit whose text is not found in the document is skipped.

## Decisions and types

| Type | Shape | Description |
| --- | --- | --- |
| `RichTextEditor5Decision` | `{ action: 'accept' \| 'reject'; change }` | One suggestion was decided. |
| `RichTextEditor5Decision` | `{ action: 'accept-all' \| 'reject-all'; changes }` | Every suggestion was decided; `changes` is the list as it was before. |
| `RichTextEditor5Change` | `{ id, kind, before, after, author, createdAt }` | `kind` is `insert`, `delete` or `replace`; `before` is the struck text and `after` the inserted text. |
| `RichTextEditor5Task` | `'spelling' \| 'tighten' \| 'summary' \| 'checklist' \| 'questions' \| 'owners'` | The six tasks. Only `spelling`, `tighten` and `summary` can be limited to a passage. |

## Limits

- The assistant has no model. The local planner only knows its fixtures: five typos, two rewrites, one summary and one checklist, so on another document most tasks find nothing.
- Only inline text edits and whole new blocks are suggestions. A block the assistant adds is created directly and its text is the suggestion; rejecting it removes the empty block.
- A `replace` or `insert` edit finds text by exact match inside one block; text that spans two blocks is not found.
- Stop keeps the suggestions already written; it does not undo them.
- The undo button calls the editor history: it reverts the last decision only while nothing else was edited after it.
- Formatting, block type changes and paragraph splits are direct edits and never appear as suggestions. There is no toolbar; formatting comes from keyboard shortcuts and markdown.
- The card covers the end of the lines under it; collapse it to read the whole page.

## Accessibility and theme

- The card is an `aside` named by `labels.dock` and its chat is a `section` named by its `h2`. Collapsed, it is a button named by its visible text and the pending count.
- The empty state is a `status`; its task buttons are a `group` named by `labels.tasksGroup`. The conversation is a `log` named by `labels.conversation`.
- The `/` list is the composer listbox: options are disabled while a run is active, and tasks that cannot take a passage are disabled while one is handed.
- The status line of the latest answer is an `output` with `aria-live="polite"`: a run announces what it is doing and how it ended. Earlier answers keep their status as plain text.
- The step trace is an ordered list; the state of each step is also in `data-state`.
- The labelled caret is decoration (`aria-hidden`); the trace and the status carry the same information.
- Insertions and deletions are `ins` and `del`, so meaning does not depend on color: deletions are struck through and insertions are underlined.
- Accept and Reject buttons are named with the author and the text, so each one is distinct.
- Buttons use the `sm` and `icon-sm` sizes. Colors come from tokens; the `success` and `destructive` foreground tokens keep contrast on the card background.
- The composer placeholder uses the full `muted-foreground` token instead of the COSS 72%, registered in `scripts/override-exceptions.json` with the same ratios as the `AssistantComposer`.
