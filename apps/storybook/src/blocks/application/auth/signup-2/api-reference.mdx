# Signup2

The minimal sign-up page: name, e-mail, a password with live feedback and a confirmation, both with a show and hide button, and the submit button, inside a centered card. It has no logo, no providers, no terms notice and no links. Reach for it when the app only needs the account data, or as the smallest page to edit into your own. Install it with `npx @tc96/parttens add signup-2`.

It is a whole page, not a form to place inside one: it renders its own `main` landmark. Account creation, the session, cookies and redirects stay in the app; the block only calls `onSubmit`, and it never fetches or stores anything. For the logo, the providers, the terms notice and the sign in link, use [Signup1](?path=/docs/blocks-auth-register-register1-api-reference--api-reference).

The other pages of `Blocks/Application/Auth/Register/Register2`: [Playground](?path=/story/blocks-auth-register-register2-playground--playground) to try the errors, the pending state and the password rules, [Stories](?path=/story/blocks-auth-register-register2-stories--default) for the pending, error, field error and password rule states, [Behavior](?path=/story/blocks-auth-register-register2-behavior--page-heading) for the tests and [Usages](?path=/story/blocks-auth-register-register2-usages--create-account) for real sign-up screens.

## Import

```tsx
import { Signup2 } from '@acme/blocks/application/auth/signup-2'
```

The same path exports the types `Signup2Props`, `Signup2Values`, `Signup2Labels`, `AuthPasswordSuggestion`, `AuthNewPasswordLabels` and `AuthFieldErrors`.

## Signup2

The whole sign-up page. Renders a `main` that fills the window height and centers its content, and inside the card the title (an `h1`), the description, the form message and the form. Mount it on the route and do not wrap it in another `main`. It only takes the props below.

| Prop | Type | Default | Description |
| --- | --- | --- | --- |
| `onSubmit` | `(values: Signup2Values) => void` | required | Called with `name`, `email` and `password` after the constraints and the confirmation pass; never while `pending`. |
| `passwordMinLength` | `number` | `8` | Sets the native `minLength` of the password. |
| `passwordSuggestions` | `AuthPasswordSuggestion[]` | `["lowercase", "uppercase", "number", "symbol"]` | Lists the character types the feedback suggests; an empty list hides them. |
| `pending` | `boolean` | `false` | When true, disables the submit button, puts the submit button in its `loading` state and sets `aria-busy` on the form. |
| `error` | `string` | - | Shows a message for the whole form in an alert titled `labels.errorTitle`. |
| `fieldErrors` | `Partial<Record<keyof Signup2Values, string>>` | - | Shows a message under each field it names (`name`, `email` or `password`) and marks that field invalid. |
| `labels` | `Partial<Signup2Labels>` | - | Overrides the texts the block owns; each missing key keeps its pt-BR default. |

| Attribute | Values | Description |
| --- | --- | --- |
| `data-slot` | `"card"` | Marks the card, which holds everything |
| `data-slot` | `"form"` | Marks the form; it carries `aria-busy` |
| `data-slot` | `"field-description"` | Marks the password feedback: the length and the suggestions |
| `data-met` | present when met | On the `li` of a suggestion the password already satisfies |

### Submit

`onSubmit` runs when the form is submitted by the button or by Enter. It runs only after the native constraints pass (`required` on every field, `type="email"` on the e-mail and `minLength` on the password), only when the password and the confirmation match, and never while `pending`. The password confirmation adds nothing to the values. The return value is ignored. The fields are uncontrolled, so what the user typed stays in the form after an error. The messages of the native constraints are the browser's own and have no label.

### Confirmation

After the native constraints, the block checks that both password fields are equal. When they differ it shows `labels.passwordMismatch` under the confirmation, marks it `aria-invalid`, moves focus to it and does not call `onSubmit`. The message clears when either password field is edited. The confirmation is not a key of `Signup2Values`, so `fieldErrors` cannot target it, and its value never leaves the block.

### Password feedback

Under the password field, the block shows one item per entry of `passwordSuggestions`. The items sit inline on one line: a circle while missing and a check in the `success` color once met. The state is not shown as text; screen readers read `labels.suggestionMet` or `labels.suggestionMissing` from visually hidden text. The feedback is advice: only `passwordMinLength` blocks the submit. It describes the password field through `aria-describedby`, and a polite live region announces only when a suggestion changes state, not on every key.

Values of `AuthPasswordSuggestion`: `"lowercase"`, `"uppercase"`, `"number"` and `"symbol"`.

### Errors

- `error` is rendered as text, never as HTML. When it goes from empty to a message, focus moves to the alert, unless `fieldErrors` names a field, which takes the focus.
- `fieldErrors` ties each message to its field with `aria-invalid` and the field's error text. When it goes from empty to filled, focus moves to the first of those fields in the form. A message clears when the user edits its field.
- Both are the app's state: the block never sets either of them.

### Signup2Values

## Accessibility and theme

- The page has one `main` landmark and one `h1`, the card title; do not wrap the block in another `main`.
- Both password buttons are named by `labels.showPassword` and `labels.hidePassword`; override both when you translate the block.
- The block carries no theme rule: it reads the card, field, button and alert tokens of the theme it renders in.
