# Blocks

Installable blocks: numbered variations of a page, a page frame or a page section that compose ui components (COSS, `Text`, `IconFrame`), `helpers` and pattern modules, copied into the consumer by `tc96 add <block>` and edited there ([ADR 0009](../../.specs/adr/0009-blocks-layer.md), which turned the installable templates of [ADR 0005](../../.specs/adr/0005-installable-templates.md) into blocks). Blocks live in categories (`application`, `auth`, `data`, `charts`, `solutions`, `ai-agents`, `ecommerce`, `marketing`); `docs/architecture/layer-decision-map.md` decides whether new code is a block and which category it takes. The first group is `application/shell/` with `AppShell1` to `AppShell4`; the second is `ai-agents/flow/` with `WorkflowEditor`, `AgentBuilder`, `RunMonitor` and `ImpactMap`; the fourth is `application/settings/` with `Settings1` to `Settings23`: 1 to 16 are the settings screens that were usage stories of the `surfaces/settings` pattern, 17 to 23 are new variations; the third is `application/auth/`, whose blocks are `Login1`, `Login2`, `Login3`, `Login4`, `Login5`, `Otp1`, `Signup1`, `Signup2`, `ResetPassword1`, `ResetPassword2`, `ForgotPassword1`, `ForgotPassword2`, `Login6` to `Login10`, `Signup3`, `Signup6`, `ResetPassword6` and `MagicLink6` (`ResetPassword2` is a variation beyond the first five, requested after the first delivery). A block is controlled like a pattern: data comes through props, links through `renderLink`, events through callbacks; it never fetches, persists, reads cookies or applies a theme. Blocks consume patterns; a pattern never imports a block. The screens that only live in Storybook (`Templates/Contacts` and the other CRM pages) stay in `apps/storybook/src/templates/` under [ADR 0004](../../.specs/adr/0004-templates-only-in-storybook.md) and are not blocks.

## Invariants

- Every block folder is reachable as `@tc96/ui/blocks/<category>/<group>/<block>`, or `@tc96/ui/blocks/<category>/<block>` for a flat category such as `auth`, through the package `exports` (`./*` to `./src/*/index.ts`) and installs to the same path under the consumer's `blocks` alias (`blocks/application/auth/login-1`).
- `shared/` files are not re-exported by a block `index.ts`; only types are. Renaming a `shared/` file changes the files every installed shell carries.
- A data block takes `pending`, `error` and `onRetry`: `pending` renders its internal `<block>-skeleton.tsx` (`aria-busy="true"`, named by `labels.loading`) in place of the content and keeps the section header; `error` renders the error `StateSurface` with `labels.errorTitle` and `labels.errorDescription`, and a `labels.retry` button only with `onRetry`. `pending` wins over `error`, which wins over the empty state; in a settings block with several sections, only the first stays and holds the state (`settings/shared/settings-load-state.tsx`).
- Every visible or accessible text is a key of the block's labels type (`ShellLabels`, `AuthCommonLabels` and each auth block's own `*Labels`) with a pt-BR default in the group's `shared/labels.ts` or the block's `labels.ts`; `labels` is partial and merged over the defaults.
- Links render through `renderLink(href)` as the Base UI `render` element of `SidebarMenuButton`, `SidebarMenuSubButton` and `BreadcrumbLink`; the default `renderAnchor` comes from `@tc96/ui/render-anchor` (`packages/ui/src/render-anchor.tsx`, an `own` item shared by every group), which carries the `biome-ignore` because the text arrives through the render prop.
- Active items set both `isActive` (COSS `data-active`) and `aria-current="page"`. A branch with sub items starts open when it or a child is active. A leaf with `actions` shows the actions menu and drops its `badge`, because both sit at the right edge.
- `ShellSearch` owns its open state and the ⌘K / Ctrl+K listener on `document`; picking a route closes the dialog, then calls `onNavigate(href)`.
- `AppShell4` nests two `Sidebar collapsible="none"` (rail and section panel) inside one `Sidebar collapsible="icon"`, with `--sidebar-width` set to the icon width plus `16rem`; collapsing clips the panel and picking a section calls `setOpen(true)`. The workspace switcher and the account menu run `compact` in the rail, with their tooltips always shown.
- The section of `AppShell4` is controlled by `sectionId`; the block keeps no copy of it.
- `settings` turns every shell's sidebar into the settings level and keeps the shell's own variant and `collapsible="icon"`: `ShellBackButton` replaces the workspace switcher (and the search in `AppShell2`), the settings `ShellNav` is named by `labels.settingsNavigation`, and the footer, projects and usage card drop out. `AppShell4` keeps its rail, with no section active, and swaps only the panel. `settings` takes exactly one of `backHref` (link through `renderLink`) or `onBack` (`type="button"`). Settings items carry `icon`, because the sidebar still collapses to icons.
- Every shell wraps `children` in a flex column with `gap-4 p-4`; `padded={false}` drops both, for a page that runs edge to edge in the inset (the flow editors with `actionsContainer`).
- Every shell gives `SidebarInset` `min-w-0`. The inset is a flex item of the provider's row, so without it a wide child (a `DataTable`, a `KanbanView`) widens the inset past the viewport and the page scrolls sideways instead of the child's own container.
- The auth blocks are whole pages and controlled: `AuthCard` renders the `main` landmark (so the consumer wraps nothing in another `main`), the block keeps only interaction state (password visibility and, in the new password blocks, the typed value for the feedback and the confirmation mismatch) and never the submit state: `pending`, `error` and `fieldErrors` come from the consumer, and `onSubmit` does not run while `pending`. Validation is the COSS `Form` (Base UI `Form`, `noValidate`): native constraints run on submit, `errors` is keyed by `Field name` and built with `toFormErrors` inside a `useMemo`, and `useFocusFirstInvalid` covers the errors that arrive without a submit. A link renders only when its `href` is passed, through `renderLink(href)` (default `renderAnchor`). Native constraint messages are the browser's own and have no label.
- `Timeline1` to `Timeline4` own loading and error: `pending` renders the block's own skeleton (`timeline-{n}-skeleton.tsx`, not exported, root `aria-busy="true"` named by `labels.loading`, header kept) and `error` renders the `StateSurface` error with a Tentar novamente button only when `onRetry` is passed; the precedence is `pending`, then `error`, then empty, and the consumer passes the query flags instead of building a skeleton or surface.
- `Stats1` to `Stats6` own loading and error the same way (`stats-{n}-skeleton.tsx`, not exported); the card header stays, but `Stats2` hides its renewal date while loading or failed, because the date is data. Only `Stats1` has an empty state, which `error` wins over.
- `Card1` to `Card9` own loading and error the same way (`card-{n}-skeleton.tsx`, not exported); `Card2` and `Card3` render their state inside a region named by `labels.title`, and `Card3` takes `profile` as optional so the app can pass the flags before the data arrives. `Card4` to `Card6` and `Card8` have an empty state, which `error` wins over; `Card7` and `Card9` take `contact` and `delivery` as optional and show their skeleton until it arrives. `Card8` and `Card9` share the actions menu in `shared/card-menu.tsx`.
- `List1` to `List6` own loading and error the same way (`list-{n}-skeleton.tsx`, not exported); `List2` and `List3` keep their heading and filter, `List6` keeps its search, and `List1` and `List4` render the state inside a region named by `labels.title`. Every list block but `List5` has an empty state, which `error` wins over.
- `Dashboard1` to `Dashboard3` follow the same loading and error contract as the timelines with one `pending`, `error` and `onRetry` for the whole page (`dashboard-{n}-skeleton.tsx` mirrors the grid, root `aria-busy="true"` named by `labels.loading`, heading kept); the empty state shows only when every list is empty, and an empty table shows its own message row. The filter (`Dashboard1`: `filter`, `filterOptions`, `onFilterChange`), the sort (`Dashboard2`: `sort`, `onSortChange`), the search (`search`, `onSearchChange`), the page (`pagination`, `onPageChange`) and the period (`period`, `periodOptions`, `onPeriodChange`) are controlled and the block never filters, searches, pages or reorders rows; each header and table tool renders only with its callback, and the row menu (`Dashboard1`, `Dashboard2`) only with `rowActions` and `onRowAction(actionId, rowId)`. Numbers arrive raw and are formatted with `locale` and `currency`; every chart is a `role="img"` named by a label and described by a hidden text built by a label function, and sparklines are `aria-hidden`. `Dashboard3` renders the queue buttons only with `onAction(id)`, naming each by `labels.actionFor(action, title)`.
- `Otp1` keeps no value of the code: the `OTPField` is uncontrolled and the code reaches the consumer only through `onSubmit` (Verificar or Enter, a complete code, never while `pending`) and `onComplete`; `autoSubmit` stays off. The Base UI `OTPField` names only slots 2 and up from their `aria-label`; the first slot is named by the `FieldLabel` and ignores `aria-label`, so `Otp1` points its `aria-labelledby` at a hidden span with `labels.digit(1, length)`, and the field label names the group. The field error and the `fieldErrors.code` focus go through the hidden validation input the `OTPField` renders with the field `name` (`type="text"`, so the `type="hidden"` skip in `useFocusFirstInvalid` does not drop it): focusing it forwards to the first slot (`focusInput(0)` in its `onFocus`), and on a submit the `Form` focuses the first slot itself through the registered control. The resend countdown is `resendIn` from the consumer, plain text in the footer button, never in an `aria-live` region.
- `Signup1` checks the confirmation through the `Form` errors, not through a field `validate`: `onFormSubmit` compares `password` with `confirmPassword`, and on a mismatch sets a `mismatch` boolean and returns without calling `onSubmit`. The memoized `errors` passed to `Form` merges `{ confirmPassword: labels.passwordMismatch }` while `mismatch` is true, so the field is marked invalid, shows the `FieldError` and the Base UI `Form` focuses it: `submittedRef` stays set after a valid submit, and the next change of its internal `errors` runs `focusFirstInvalid`, so no manual focus is needed. A submit with the mismatch still showing is stopped by the `Form` itself (the field is invalid) and focuses the confirmation. `onValueChange` of both password fields clears `mismatch`; `confirmPassword` is not a key of `SignupValues`, so `fieldErrors` cannot reach it, and the confirmation value never leaves the block. The password value is kept in state only for `AuthPasswordFeedback`. The terms notice renders a link only for each `termsHref` and `privacyHref` passed, with `termsAnd` between two; it has no checkbox and adds nothing to `SignupValues`. With only `privacyHref`, the default `termsLead` ("... com os") reads wrong in pt-BR, so the consumer overrides `labels.termsLead` then.
- `Login2` is `Login1` reduced to e-mail, password and submit: `onSubmit({ email, password })`, the same `pending`, `error`, `fieldErrors` and focus rules, and no part that needs a prop beyond those. `Login1` keeps the optional parts and its `Layouts` page has no minimal story, because that page is `Login2`.
- `Signup2` is `Signup1` reduced to name, e-mail, the new password with its feedback, the confirmation and submit: `onSubmit({ name, email, password })`, `passwordMinLength`, `passwordSuggestions`, the same `pending`, `error`, `fieldErrors`, mismatch and focus rules, and no part that needs a prop beyond those. `Signup1` keeps the optional parts and its `Layouts` page has no minimal story, because that page is `Signup2`.
- `ResetPassword1` has no token prop, no token field and no token in `ResetPasswordValues`: the reset token is the consumer's (it reads it from the route and sends it with the new password), and an expired or invalid token comes back through `error`. It repeats the `Signup1` confirmation check (`mismatch` boolean merged into the memoized `Form` errors, cleared from both password fields) and the password feedback, with `newPassword` as the label of the first field; the back to login link is the whole footer and renders only with `loginHref`.
- `ResetPassword2` is `ResetPassword1` plus a validity timer the consumer owns: `expiresIn` (seconds left on the link) and `requestNewLinkIn` (seconds before another request) come from props, and the block runs no interval, no timeout and no clock. Without `expiresIn` it behaves exactly like `ResetPassword1`. With `expiresIn` above zero it shows `labels.linkExpiresIn(formatCountdown(expiresIn))` as plain text above the form, never in an `aria-live` region; the only live region is a sr-only one whose text appears once, when `expiresIn` is at most 60 (`labels.expiringSoon`), derived from the prop with no state. At zero or less the form is replaced inside the same `AuthCard` by the expired state (`expiredTitle`, `expiredDescription`, the back to login link, and a button only when `onRequestNewLink` is passed), so `onSubmit` cannot be called; focus moves to the expired title (`titleRef`, `tabIndex={-1}`) only on the change from not expired to expired, never on mount. The request button is disabled while `requestNewLinkIn` is above zero (text `labels.requestNewLinkIn`) or `pending`, and the callback is guarded as well.
- `Login3` is the `Login1` form plus an `aside` slot, with the form state in TanStack Form (`useForm`) and the COSS `Form` still owning the native constraints, `errors` and the first-invalid focus: `onFormSubmit` returns while `pending`, otherwise calls `form.handleSubmit()`, which calls the consumer's `onSubmit` with the TanStack values. The password field is the shared uncontrolled `AuthPasswordField`, mirrored into the form through `onValueChange`. With `aside` the block renders a `grid md:grid-cols-2` wrapper holding the `AuthCard` (the only `main`) and an `aside` (complementary landmark named by `labels.asideLabel`, outside the `main`) that is `hidden` below `md`; without `aside` it returns the `AuthCard` alone.
- `Login4` is `ForgotPassword1`'s shape for sign in: `onSubmit({ email })`, `sent`, `destination`, `resendIn` and `onResend` behave as in `ForgotPassword1` (the block never keeps the sent state, focus moves to the confirmation title only on the change to sent, the resend row renders only with `onResend`), with the form state in TanStack Form as in `Login3`. The only link is `passwordLoginHref` (`labels.passwordLogin`), rendered in both states and only when passed.
- `Login5` has no internal view state: `method` (`'email'` or absent) and `onMethodChange` are the consumer's, and nothing changes on screen if `method` does not change. Without `method='email'` the card lists `methods` (`{ id, label, icon? }`, each calling `onMethod(id)`) plus the built-in e-mail method (`labels.emailMethod`, calling `onMethodChange('email')`) in a `fieldset`; with it the same card shows the e-mail and password form (TanStack Form as in `Login3`) and a back button (`onMethodChange(undefined)`). Method buttons and the back button are disabled and guarded while `pending`. Focus moves to the e-mail field when `method` becomes `'email'` and to the e-mail method button when it goes back, never on mount.
- `ForgotPassword1` has the same form as `Login1` reduced to the e-mail (`onSubmit({ email })`, `fieldErrors.email`, `autoComplete="email"`) and keeps no "sent" state: `sent` is the consumer's. With `sent` true the form is replaced inside the same `AuthCard` by the confirmation (`sentTitle`, `sentDescription(destination)`, the resend row and the back to login link), so `onSubmit` cannot be called; `destination` is the only source of the address, the block never reads the e-mail from the form, and without it the text is generic. Focus moves to the confirmation title (`titleRef`, `tabIndex={-1}`) only on the change from not sent to sent, never on mount, and there is no extra `aria-live` region. The resend row renders only when `onResend` is passed; its button is disabled while `resendIn` is above zero (text `labels.resendIn`, plain text, never in an `aria-live` region) or `pending`, and the callback is guarded as well. `error` stays in the `Alert` in both states, so a failed resend can show; the back to login link renders in both states and only with `loginHref`.
- `ForgotPassword2` is `ForgotPassword1` reduced to the e-mail form and the confirmation: `onSubmit({ email })`, `sent`, `destination`, the same `pending`, `error`, `fieldErrors` and focus rules (the title takes focus only on the change to `sent`), with no `logo`, no `loginHref`, no `onResend` and no `resendIn`. `ForgotPassword1` keeps the optional parts and its `Layouts` page has no minimal story, because that page is `ForgotPassword2`.

- Both flow blocks keep the selection, the steps and every result in the consumer (`selectedStepId` and `onSelectedStepChange` are props); the block state is the inspector (open, `view` | `edit` | `create`, tab, log filter), the assistant (open, expanded), `snapToGrid`, `locked` and the two confirmation dialogs.
- A library click or a canvas drop calls `onStepAdd(type, { position? })` at once; the header Adicionar passo, the node "+" and Adicionar ramo open the inspector in `create` mode, and submitting calls `onStepAdd(type, { after?, connection?, values })`. Saving the edit form calls `onStepChange(stepId, values)`. Deleting a step with connections asks through an `AlertDialog` first.
- `onStepsChange` receives the whole list. Reorganizar (workflow, `horizontal`) and Organizar árvore (agent, `vertical`) pass `tidyTree` the `flowStepNodeSize` and a gap of 96 by 48 and 48 by 88.
- `locked` makes the block read-only for mutations: `createFlowEditorHandlers` ignores `add-after`, `add-branch`, `duplicate`, `delete`, the library add, the drop, the tidy and the create submit, and the controls render `disabled` (header Adicionar passo, Reorganizar and Organizar árvore, the library items, the inspector delete and the create submit). `view` and `edit` stay enabled.
- `onStepsChangeEnd(steps)` is forwarded from the canvas (one call per drag) and also called once after a tidy, so a consumer records one undo entry per gesture; the story fixture `use-flow-editor-state.ts` does it.
- The form validates only the name (`FieldError`, `aria-invalid`, focus on the field). Caminho is the label of the first incoming connection; Responsável matches `step.owner.name` against `owners`.
- Below `md` the library is `collapsed`, the inspector is the `Sheet` of the pattern and the assistant is a full-screen COSS `Sheet` (`data-slot="flow-assistant-fullscreen"` on the popup; role, focus trap and Escape, which closes it) with `placement="docked"`; from `md` the assistant is `floating` in the canvas wrapper, which is the positioned ancestor.
- `AgentBuilder` takes `actionsContainer`, an element in the consumer's app header (the `actions` slot of an App Shell): when set, `FlowPageActions` renders there through `createPortal`, the page drops `FlowPageHeader` (the shell carries the breadcrumb) and `FlowPageLayout` renders with `framed={false}`, without `rounded-xl border` and with `p-4` on the canvas pane (`flow-page-canvas`) in place of the shell padding; `null`, while the slot mounts, renders no actions. The story passes it through `withAppShell({ actionsArg })`, which also drops the root crumb with `root: false` and the shell padding with `padded: false`.
- The page frame (`flow-page`) takes `min-h-160` and `flex-1`, so it needs a flex column parent with a height, like the content area of the shells.
- The settings blocks hold no setting value: switches, selects and lists come from props (`checked`, `value`, the arrays), and every change is a callback; reordering, the default account and created items are the consumer's. A row actions menu and a create button render only when their callback is passed. The e-mail form of `Settings1` is the only form with a submit and runs on TanStack Form (`@tanstack/react-form`) with the COSS `Field`. No control uses an `xs` size.

## Styling

- `RunMonitor` and `ImpactMap` own loading and error like the timelines: `pending` renders `run-monitor-skeleton.tsx` or `impact-map-skeleton.tsx` (`aria-busy="true"`, named by `labels.loading`, heading kept), `error` renders the error `StateSurface` with a Tentar novamente button only with `onRetry`, and the precedence is `pending`, then `error`, then empty. Neither block fetches or runs a timer.
- `RunMonitor` is read-only: the canvas is always `locked`, and the five statuses (`pending`, `running`, `succeeded`, `failed`, `waiting-approval`) map to the canvas `not-run`, `running`, `success`, `failed` and `idle` with `labels.statuses` as the canvas labels. Aprovar and Recusar render only for steps `waiting-approval` and only with `onApprove` and `onReject`, each called with the step id; Reexecutar renders only with `onReplay`; every button is `size="sm"` and the approval buttons carry the step name in `aria-label`.
- `ImpactMap` is controlled: a node click calls `onNodeSelect(id)` and never changes the highlight; `selectedId` sets `aria-pressed` and `data-selected` and the `border-primary ring-primary` tokens. The tree grows from the node that is never a `source`: `links` go from the contributing node to the one it feeds, and the block reverses them for `tidyTree`; `progress` is clamped to 0 to 100.
- The flow blocks add no override on a COSS part; the page frame is a plain `div` with `border` and `rounded-xl` on tokens. Their contrast ratios are in `docs/accessibility.md` (Editores de fluxo).
- No border, radius, color or shadow class on a COSS part except where listed in `scripts/override-exceptions.json`; layout, size and typography classes are allowed (`SidebarHeader className="h-14 justify-center px-4"`, `Separator className="me-2 h-4"`, `Badge className="absolute -end-1 -top-1"`).
- `AvatarFallback className="text-foreground"` in `shared/user-menu.tsx`: the fallback sits on `bg-border` and inherited the muted `sidebar-foreground` (3.83:1 light). Registered in `scripts/override-exceptions.json`; the ratios are in `docs/architecture/tc96-ui.md` (Templates: App Shells).
- The workspace logo is an `IconFrame` with `bg-sidebar-primary text-sidebar-primary-foreground`, the sidebar's own pair; `bg-muted` vanished on `bg-sidebar` in dark.
- `UsageCard` and the notification rows are block elements on sidebar or popover tokens (`bg-sidebar-accent text-sidebar-accent-foreground`, `hover:bg-accent`).
